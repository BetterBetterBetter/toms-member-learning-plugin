## Audit gate l8-ratelimit-0.9.0.1: FAIL

The new cache path is sound for Redis Object Cache, the drop-in TSOL is set up for. It fails open on other drop-ins it accepts.

**What I ran:** PHP and Docker aren't available on this host, so I used a static PHP 8.3 binary in `/tmp/l8php`. Lint passes, the harness passes all 40 checks, and the mutation check kills all 9 mutants. CI lints on PHP 8.0, which I didn't run; a manual scan of the new files found no PHP 8.1+ syntax. I checked the logic against the source of Redis Object Cache 3.0.1-dev and Pantheon's WP Redis. Both findings below reproduce against the real `class-library-auth-repository.php`, using the harness's stubs with the drop-in behaviour swapped in.

### Findings

**1. Blocking: any other persistent object cache is trusted, so the auth limiter can fail open.** (`includes/features/library-auth/class-library-auth-repository.php:219`, `:237`)

`rate_limit_cache_usable()` accepts any drop-in for which `wp_using_ext_object_cache()` is true. `rate_limit_cache_connected()` returns **true** when the drop-in has no `redis_status()` method. The safety rules this relies on (atomic `add`, atomic `incr`, and detecting a fall-back to a per-request array) are only checked for Redis Object Cache. That contradicts "Never fails open" (`:166`) and the changelog's "Fails closed".

Concrete case, Pantheon WP Redis (checked in its source):
- `add()` is `_exists()` followed by `set()`, so it isn't atomic.
- When Redis is lost, `exists` returns false and `set()` still returns true, so `add()` returns true on every new request.
- It has no `redis_status()` method.

Results against the real code:
- **Redis down:** with a limit of 3, all 10 requests to `Rate_Limiter::check('token', …)` are allowed and nothing is written to SQL. The limiter is effectively off.
- **Redis up:** two concurrent first requests both get count 1. Each window over-admits by the size of the parallel burst.

This plugin serves both brands (`RELEASE.md`), and nothing in the repo says which drop-in Liberty runs.

**Fix:** use the cache only when `$wp_object_cache` exposes `redis_status()` and it returns true; send every other drop-in to SQL. The harness can't catch this because its fake always has `redis_status()`. Add a case for a drop-in without it, plus a mutant that restores the current default.

**2. Should fix, not blocking: `WP_REDIS_MAXTTL` of 0 skips the guard but removes every TTL.** (`:226`)

When `WP_REDIS_MAXTTL` is defined, Redis Object Cache's `validate_expiration()` caps every TTL to that value, so 0 means "no expiry". Its README lists `0` as the default, so defining it as 0 is a plausible copy of the documented default.

Reproduced result:
- The `w:` and `c:` keys are stored with no TTL, leaving two permanent keys per distinct rate key. Scopes keyed by IP address can create these without limit.
- From about 3 s after the first window ends, every request for that key makes two Redis calls first and then goes to SQL (1, 2, 3 SQL writes at t0+63, +200, +5000).

It still fails closed, so it's not a bypass.

**Fix:** remove `(int) WP_REDIS_MAXTTL > 0 &&` from the condition. The harness fake never applies MAXTTL to TTLs, so it can't catch this either.

### Non-blocking notes
- `wp_cache_flush()` empties the whole Redis database unless selective flush is on, so it resets every counter. Redis memory eviction can also drop these short-TTL keys first (always under `volatile-ttl`). The SQL table never lost counts this way. Worth one line in the README.

### Checked and correct for Redis Object Cache
- When Redis is connected, `add` is `SET NX EX` and doesn't consult the per-request copy; `incr` is `INCRBY` and keeps the TTL.
- The igbinary guard matches the drop-in's own `use_igbinary` condition exactly.
- Converting `:` to `-` in keys keeps them distinct.
- Concurrent first requests, window rollover, the counter-recreated-at-1 path, losing Redis mid-request, and the forced re-read of the window key all behave correctly.

### Assumption
I couldn't establish either live site's drop-in. An earlier session says Redis Object Cache 3.0.0 is staged but inactive on School of Life; Liberty's is unknown. I didn't add this to `docs/assumptions/` because this run is review-only.

VERDICT: FAIL
